# 个人开发版范围与代码清理规范

> 最后核对：2026-08-27；适用范围：PetCare 后续需求、实现、代码审查、测试、文档和演示数据

## 1. 目的与事实源

PetCare 当前按个人、非商业、可本地验收的产品原型维护。本规范用于防止未来商业设想继续进入当前产品，并规定已有商业原型代码的清理方式。

发生冲突时按以下顺序判断：

1. [当前状态与开发路线图](../01-requirements/05-development-roadmap.md)决定当前范围和下一执行节点；
2. 本文决定范围落实和代码清理方式；
3. [PRD](../01-requirements/01-prd.md)与[原型规格](../01-requirements/04-prototype-specification.md)中的商业服务章节只作为未来设计资料；
4. 历史计划、页面、接口、数据库模型和测试的存在不能自行恢复需求。

任何人不得仅因为“代码已经存在”就把暂停能力描述为当前能力、继续补全其功能或重新放回导航。

## 2. 当前允许开发的范围

当前只允许主动开发和完善以下能力：

- 本地账户与会话、个人资料和本人宠物档案；
- 萌宠课堂、受控社区、审核/举报、互动和最小站内通知；
- 与上述能力直接相关的 Admin 内容治理、RBAC 和 Website 内容读取；
- 本地 Docker Compose、持久化本地媒体、隔离 E2E、缺陷修复、安全和依赖维护；
- 已由路线图明确列入个人版队列的小范围可用性、无障碍和性能改进。

新增需求必须先进入路线图，并说明用户价值、权限边界、失败状态、测试证据和是否依赖外部主体或账户。未进入路线图的功能不得直接实现。

## 3. 当前禁止扩展的范围

以下能力统一属于未来商业版，禁止新增、补全、接线、暴露入口或制作看似真实的演示数据：

- 服务者实名认证、人脸识别、资质审核、评分接单资格和对外招募；
- 悬赏发布、接单、订单状态机、SOP 履约、服务监控、取消、评价和投诉裁决闭环；
- 微信支付、退款、对账、分账、结算、提现、钱包、优惠券和收费配置；
- B2C 平台定价、派单、服务保障、保险、实时聊天和规模化运营；
- 需要企业主体、生产合同、合规材料、公开审核或真实资金责任的发布与经营能力。

不得使用“即将上线”按钮、可点击空页面或环境变量开关在当前产品中暗示这些能力。未来概念只能留在明确标记的产品文档中。

## 4. 清理原则

### 4.1 先关闭能力，再删除实现

清理顺序必须从外到内：先移除用户入口和默认运行时注册，再删除已经没有当前消费者的页面、Mock、API 客户端、资源和测试。不得先删除数据库结构或共享底层代码，造成迁移链、历史数据或仍在使用的公共能力损坏。

### 4.2 删除优先于伪禁用

仅服务于暂停商业范围的导航、按钮、路由和静态页面应直接从当前构建中移除。不要保留可点击但弹出“暂未开放”的入口，也不要用 CSS 隐藏仍可通过键盘、深链或直接 URL 到达的页面。

### 4.3 保留必须有理由

代码只有在满足以下至少一项时才能暂时保留：

- 当前个人版仍有调用者；
- 删除会破坏已提交迁移、历史数据兼容或共享基础设施；
- 它是用于验证当前范围安全边界的回归测试；
- 路线图明确要求在后续清理节点处理。

保留的商业代码不得注册到当前导航、公开路由、默认种子数据或默认运行模块中。不得为了“以后可能用”继续维护其新功能。

### 4.4 数据与迁移单独处理

Prisma 模型、既有 migration、数据库记录和对象存储文件不属于普通死代码：

- 禁止手改或删除已提交 migration；
- 禁止在界面清理提交中顺带删除表、字段或用户数据；
- Schema 收缩必须另建任务，先完成引用审计、数据保留决策、可恢复备份和新 migration；
- 演示数据清理必须先冻结精确记录，只删除可识别的旧商业演示数据，并保护后续或用户创建的数据。

## 5. 清理分类

| 分类           | 处理方式                                                   | 典型内容                                                                   |
| -------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| 当前必须删除   | 从导航、路由、默认内容和构建引用中移除；无消费者后删除文件 | 静态悬赏、服务订单、钱包、提现、照护者招募和“服务进行中”入口               |
| 当前必须隔离   | 不进入默认运行时或公开 API；保留代码与测试等待后续独立决策 | 订单、服务者认证、投诉裁决、SOP/费用等已形成持久化边界的 Server/Admin 模块 |
| 当前继续维护   | 保持真实数据、权限、状态和测试                             | 账户、宠物档案、课堂、受控社区、内容治理、RBAC、本地运行                   |
| 历史资料保留   | 明确标记为 future/history，不作为验收或 backlog            | PRD 商业章节、完整原型、历史实施计划                                       |
| 高风险后续清理 | 只有独立迁移/数据任务获批后处理                            | Prisma 商业模型、已提交 migration、历史订单或认证数据                      |

“隔离”不是永久状态。完成入口清理后，应再次进行依赖审计；确认没有当前消费者且删除风险可控的应用层代码，应在独立提交中继续删除。

## 6. 初始清理清单

以下是 2026-08-27 的初始范围，不代替执行时的引用搜索。

### 6.1 Miniapp

- 从 `MainTabLayout.vue` 和首页移除悬赏、服务订单、照护者、价格与服务进行中入口；
- 从个人中心移除订单、服务者、收藏服务、钱包、充值和提现入口；
- 注销 `pages/bounty`、`pages-bounty`、`pages-care` 及其他纯商业页面路由；
- 删除不再被当前页面使用的静态业务数据、图片、辅助函数和对应页面测试；
- 保留社区互动消息，不把订单消息或静态未读数伪装成真实数据。

### 6.2 Website 与默认内容

- 清理默认内容中的悬赏服务、平台服务、宠托师招募、服务保障和可经营承诺；
- 清理仅服务于上述内容的 CTA、导航项、页面和兜底文案；
- 保留品牌介绍、宠物内容、课堂文章、隐私/条款和当前真实能力说明；
- 已发布数据库内容不随代码静默删除，运行数据修正使用单独、可审计的内容发布或精确清理流程。

### 6.3 Admin 与 Server

- 从 Admin 当前导航和路由注册中移除订单、服务者认证、投诉裁决及商业系统设置入口；
- 默认运行时不得对个人版暴露新建悬赏、接单、认证、财务或结算能力；
- Server 商业模块先审计注册关系、数据依赖和迁移影响，再决定隔离或删除；
- 共享的上传、安全、审计、内容治理和并发基础能力不得因商业模块清理而误删。

### 6.4 文档、测试与资源

- README、当前路线图和运行说明只描述当前能力；
- 商业 PRD、原型和历史计划保留 future/history 标签；
- 删除只验证已删除静态页面的测试，保留当前能力及共享安全边界的测试；
- 删除无引用资源前必须搜索代码、样式、配置和测试，不能只看文件名判断。

## 7. 执行顺序与提交边界

代码清理按以下顺序执行，每一步都必须保持仓库可构建：

1. 建立当前入口、路由、默认种子内容、API 注册和依赖清单；
2. 清理 Miniapp 导航、首页、个人中心和商业页面路由；
3. 清理 Website 导航、默认内容、商业页面及兜底文案；
4. 清理 Admin 商业菜单和路由，并隔离默认 Server 商业 API；
5. 删除无消费者的页面、客户端函数、Mock、资源和专属测试；
6. 运行当前个人版纵向验收，更新路线图中的清理状态；
7. 只有另行批准时，才设计数据库 Schema 与历史数据清理。

提交按可观察边界拆分：Miniapp 界面清理、Website 内容清理、Admin/Server 隔离、死代码删除和数据迁移不得混成一个提交。提交标题描述实际删除或隔离的能力，不使用阶段编号代替变更内容。

## 8. 验收规则

每批清理至少满足以下条件：

- 当前导航、首页、个人中心、Website CTA 和 Admin 菜单不再暴露该批暂停能力；
- 已移除路由不能通过深链、直接 URL、键盘或残留按钮访问；
- 默认种子内容和正式代码不包含看似真实的服务者、订单、收益或资金数据；
- 没有悬空导入、失效路由、未使用资源、孤立 API 客户端或仅服务于已删除页面的 Mock；
- 当前账户、宠物档案、课堂、社区、内容治理和本地运行不回归；
- 执行与改动范围匹配的 lint、typecheck、测试和目标构建；导航或路由变化至少验证 H5 与微信小程序目标构建；
- 使用限定目录和明确 allowlist 做文本搜索，不能要求未来设计文档或隔离后端代码中的商业词汇全仓归零；
- 文档、代码、运行数据和 Git 提交状态分别报告，未执行的数据库或生产数据清理不得宣称完成。

## 9. Code Review 检查清单

审查每个后续变更时确认：

- [ ] 工作项存在于当前路线图，而不是仅存在于未来 PRD 或历史计划；
- [ ] 产品文案只陈述当前可运行能力；
- [ ] 没有重新加入悬赏、接单、认证、支付、结算或提现入口；
- [ ] 测试数据有明确隔离和清理生命周期，不伪装为正式数据；
- [ ] 删除范围经过调用、路由、资源和数据依赖搜索；
- [ ] Schema、migration 和运行数据没有被普通重构顺带删除；
- [ ] 验收命令与受影响表面匹配，失败和未验证门禁已明确披露；
- [ ] 提交没有混入无关重构、格式化或产品范围扩张。

## 10. 恢复商业范围的条件

未来只有同时满足以下条件，商业能力才能重新进入开发：

1. 用户明确决定恢复具体能力，而不是笼统恢复完整 PRD；
2. 已确认所需主体、账户、合同、合规和运营责任；
3. 路线图重新列入该能力并给出依赖、风险、验收和停止条件；
4. 对保留代码重新进行安全、数据完整性和依赖有效性审计；
5. 产品界面只在真实纵向链路通过后开放入口。

在这些条件满足前，历史代码只能被清理或隔离，不能继续扩展。
