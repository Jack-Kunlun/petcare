# 宠托师认证审核模块设计

## 1. 目标

在后台“用户管理”模块中增加宠托师认证审核子页面，完成认证申请列表、申请详情、
审核通过和填写原因后驳回的管理闭环，并完整记录审核管理员与审核时间。

本期不实现多级审批、审批转交、批量审核、撤销审核或管理员修改用户申请资料。

## 2. 领域边界

### 2.1 认证申请

`ProviderCertificationApplication` 表示用户提交的一次宠托师认证申请，独立保存：

- 申请人及申请时的认证资料快照；
- 实名与培训相关信息；
- 当前审核状态；
- 驳回原因；
- 审核管理员；
- 申请时间与审核时间。

用户重新申请时创建新记录，历史申请不得覆盖或删除。

### 2.2 宠托师当前状态

`Provider` 只保存用户当前是否已经取得宠托师认证等生效结果，不承担认证申请历史的职责。

审核通过时，服务端在同一数据库事务中将申请标记为已通过，并更新对应 Provider 的认证状态。
审核驳回时只更新申请及审核记录，不授予认证资格。

## 3. 状态模型

认证申请包含以下状态：

- `pending`：等待管理员审核，可以执行通过或驳回；
- `approved`：审核通过，申请只读；
- `rejected`：审核驳回，申请只读，必须包含驳回原因。

只有 `pending` 可以转为 `approved` 或 `rejected`。已完成审核的申请不能重复处理。

## 4. 共享契约

请求参数、响应类型和业务状态统一定义在 `@petcare/shared-types`，Admin 和 Server 禁止重复声明。

共享契约包括：

- 认证申请状态及每个状态的业务说明；
- 管理端认证申请分页查询参数；
- 认证申请列表项；
- 认证申请详情；
- 审核通过请求与响应；
- 审核驳回请求与响应；
- 分页响应。

HTTP 契约中的时间统一使用 ISO 8601 字符串。

## 5. 服务端设计

新增 `provider-certification` 业务模块，提供以下管理员接口：

- `GET /admin/provider-certifications`：分页查询认证申请；
- `GET /admin/provider-certifications/:id`：查询认证申请详情；
- `POST /admin/provider-certifications/:id/approve`：审核通过；
- `POST /admin/provider-certifications/:id/reject`：填写原因并驳回。

所有接口要求管理员 Access Token 和管理员角色。

列表支持：

- 页码与每页条数；
- 手机号、账号或昵称关键词；
- 申请状态；
- 默认按待审核优先、申请时间倒序排列。

驳回原因去除首尾空白后长度必须为 2–500 个字符。

审核操作在事务内重新检查申请状态。若申请不存在，返回资源不存在错误；若已经被其他管理员处理，
返回业务冲突错误。接口不得静默覆盖现有审核结果。

Server DTO 负责运行时校验与 Swagger 元数据，并通过 `implements` 对齐共享契约。

## 6. Admin 设计

在“用户管理”模块中增加“用户列表 / 认证审核”二级导航。

页面结构：

```text
src/pages/UserManagement/
├── index.tsx
└── Certification/
    ├── index.tsx
    ├── index.test.tsx
    ├── Detail.tsx
    └── Detail.test.tsx
```

API 统一放在：

```text
apps/admin/src/api/provider-certifications.ts
```

认证审核列表展示：

- 申请人昵称；
- 手机号；
- 实名状态；
- 培训状态；
- 申请时间；
- 审核状态。

详情页展示申请资料与已有审核记录。待审核申请显示审核操作；已完成申请只读。

“审核通过”使用确认对话框。“驳回申请”使用表单对话框，必须填写合法原因。

页面必须覆盖加载中、空数据、接口失败、权限不足和并发审核冲突状态。审核成功后刷新详情与列表缓存。

## 7. 数据一致性与安全

- 审核通过与 Provider 状态更新必须处于同一事务。
- 通过条件更新或事务内状态检查避免重复审核。
- 列表和详情只返回显式白名单字段，不返回身份证号码原文、密码、Token 或其他敏感字段。
- 若详情需要显示身份资料，只返回脱敏结果和审核所必需的证明材料地址。
- 审核管理员由当前登录态获得，禁止客户端传入或覆盖。
