# 订单投诉与纠纷完整闭环设计

## 1. 背景

PetCare 后台已具备用户管理、宠托师认证审核和订单管理，但尚未实现订单投诉、申诉、裁决及裁决结果执行。PRD 要求形成“投诉发起 → 被投诉方申诉 → 平台初次裁决 → 二次申诉 → 最终裁决”的完整闭环。

投诉与退款、结算、信用调整都围绕具体订单发生，因此本模块归属“订单管理”，后台名称统一为“投诉与纠纷”。用户详情可以展示相关案件入口，但不承载纠纷处理流程。

## 2. 目标与范围

本期一次性完成以下能力：

- 订单相关方创建投诉并提交陈述、诉求和证据。
- 被投诉方提交一次首次申诉。
- 管理员领取和转交案件。
- 管理员作出初次裁决。
- 初次裁决后的 72 小时内，投诉双方任意一方可各自提交一次二次申诉。
- 管理员基于新增理由或证据作出最终裁决。
- 最终裁决后关闭案件，不再接受申诉。
- 裁决事务内记录退款、结算和信用调整方案，并创建内部执行任务。
- 完整记录领取、转交、陈述、申诉、裁决和任务执行时间线。
- 后台提供工作队列、案件详情、裁决工作台和执行失败重试。

本期不接入微信支付、真实退款或真实结算通道。内部执行任务先完成平台内状态、金额计划和信用数据的幂等处理；未来接入支付渠道时替换任务执行器，不改变纠纷接口和页面结构。

## 3. 方案选择

采用“纠纷聚合 + 显式状态机 + 独立历史记录”方案。

`Complaint` 只保存案件当前事实，陈述、申诉、裁决、分配历史、领域事件和执行任务分别建模。所有状态变化必须经过纠纷领域服务，在数据库事务中校验当前状态、权限和版本后写入。

不采用以下方案：

- 单表工作流：会产生大量阶段相关可空字段，难以维护两级裁决和完整审计。
- 通用工作流引擎：当前没有足够的复用场景，抽象和运维成本超过收益。

## 4. 领域模型

### 4.1 Complaint

纠纷聚合根，保存：

- 关联订单、投诉方和被投诉方。
- 投诉类型、期望解决方案和当前状态。
- 当前负责人。
- 初裁后的二次申诉截止时间。
- 创建、更新、结案时间。
- 乐观并发版本。

一笔订单最多存在一个未关闭纠纷。历史已结案纠纷是否允许再次创建，由订单投诉期限和业务规则判断，不能仅依赖 `orderId` 全局唯一。

### 4.2 ComplaintStatement

保存不可变的当事人材料：

- 投诉方首次陈述。
- 被投诉方首次申诉。
- 投诉方或被投诉方的二次申诉。
- 文本理由、证据 URL、提交人和提交时间。

数据库约束保证同一案件、同一阶段、同一提交方最多一条材料。二次申诉必须包含新理由或至少一项新证据。

### 4.3 DisputeDecision

分别保存初次裁决和最终裁决：

- 裁决级别。
- 责任划分。
- 裁决理由。
- 退款金额、结算金额。
- 双方信用分调整。
- 裁决管理员和裁决时间。

同一案件每个裁决级别最多一条记录。裁决记录一经提交不可编辑，只能通过下一阶段裁决形成新的最终事实。

金额统一以最小货币单位整数保存，禁止使用 `Float`。退款与结算方案必须满足订单可处分金额边界，不能产生负数或超过订单实付、待结算金额。

### 4.4 ComplaintAssignment

记录领取和转交：

- 原负责人、目标负责人。
- 操作类型、操作人、原因和时间。

当前负责人同时冗余在 `Complaint`，用于高频工作队列查询；分配历史作为不可变审计记录。

### 4.5 ComplaintEvent

记录面向管理员和用户展示的案件时间线：

- 投诉创建。
- 首次申诉和二次申诉。
- 案件领取、转交。
- 初次裁决、最终裁决。
- 申诉期超时。
- 撤诉、结案。
- 执行任务成功或失败。

事件保存类型、操作者、发生时间和必要的结构化摘要，不复制敏感证据正文。

### 4.6 DisputeExecutionTask

保存裁决后的内部执行任务：

- 任务类型：退款、结算、信用调整。
- 幂等键。
- 任务载荷。
- 执行状态、尝试次数、失败原因和下次重试时间。

幂等键全局唯一。任务消费者必须先确认任务状态和业务目标状态，再执行更新，重复消费不得重复扣减或增加金额、信用分。

## 5. 状态机

主状态流如下：

1. `pending_response`：投诉已创建，等待被投诉方首次申诉。
2. `unassigned`：首次申诉已提交或回应期限结束，等待管理员领取。
3. `processing_initial`：管理员已领取，准备初次裁决。
4. `initial_decided`：初裁完成，进入 72 小时二次申诉期。
5. `processing_final`：任一方已提交二次申诉，等待最终裁决。
6. `closed`：最终裁决完成，或二次申诉期届满后初裁自动生效。

终止分支：

- `withdrawn`：投诉方在初裁前撤诉。
- `closed`：最终结果已经确定，不允许继续申诉。

状态规则：

- 被投诉方只能提交一次首次申诉。
- 初裁前，投诉方可以撤诉；初裁后不能撤诉。
- 初裁后 72 小时内，投诉双方各有一次二次申诉机会。
- 二次申诉提交后，案件立即进入待最终裁决，不等待另一方先提交；另一方仍可在原截止时间内补交自己的二次申诉材料，直至管理员最终裁决。
- 最终裁决提交后立即关闭案件。
- 72 小时内无人二次申诉时，定时任务确认初裁为最终结果并关闭案件。
- 最终裁决后不再开放任何申诉入口。

## 6. 权限与并发

- 只有订单相关方可以创建、查看和操作用户端纠纷。
- 管理员可以查看纠纷队列；拥有纠纷裁决权限的管理员才能领取和裁决。
- 普通管理员只能裁决自己负责的案件；超级管理员可以转交或处理任意案件。
- 管理员不能领取或裁决自己作为订单相关方的案件。
- 转交必须填写原因，并记录完整分配历史。
- 领取、转交和裁决使用状态条件与版本条件更新；受影响行数为零时返回状态冲突。
- 并发冲突不得覆盖已有结果，前端提示状态已变化并刷新最新案件。

## 7. API 与共享契约

所有请求、响应、枚举、动作可用性和分页类型定义在 `@petcare/shared-types`，Server、Admin 和 Miniapp 共同使用。分页结构固定为：

```ts
{
  list,
  total,
  page,
  pageSize,
}
```

### 7.1 用户端接口

- 创建投诉。
- 查询我的投诉列表。
- 查询投诉详情与时间线。
- 被投诉方提交首次申诉。
- 双方提交二次申诉。
- 投诉方在允许阶段撤诉。

接口返回当前状态、截止时间以及调用方当前允许执行的动作，前端不自行复制状态机判断。

### 7.2 后台接口

- 分页查询纠纷工作队列。
- 查询案件详情。
- 领取案件。
- 转交案件。
- 提交初次裁决。
- 提交最终裁决。
- 查询裁决执行任务。
- 重试失败的执行任务。

列表支持状态、投诉类型、负责人、订单号、用户关键词和时间范围筛选。

## 8. 事务与执行流程

一次裁决必须在同一数据库事务中：

1. 校验管理员权限、案件状态、负责人和并发版本。
2. 校验责任划分、退款、结算和信用调整边界。
3. 写入不可变裁决记录。
4. 更新纠纷和必要的订单状态。
5. 为每项实际影响生成带唯一幂等键的内部执行任务。
6. 写入案件事件和管理审计日志。

事务提交后，由任务消费者执行内部退款计划、结算计划和信用调整。任务失败不回滚已经形成的裁决事实，而是把案件标记为存在执行异常，进入后台异常队列。管理员只能安全重试，不允许直接修改已提交裁决。

## 9. 后台交互设计

### 9.1 信息架构

“订单管理”二级导航包含：

- 订单列表。
- 投诉与纠纷。

页面目录：

- `apps/admin/src/pages/OrderManagement/Complaint/index.tsx`
- `apps/admin/src/pages/OrderManagement/Complaint/Detail.tsx`

### 9.2 工作队列

默认展示“待我处理”，并提供：

- 待领取。
- 待回应。
- 待初裁。
- 申诉期内。
- 待终裁。
- 执行异常。
- 已结案。

列表重点显示案件编号、订单号、投诉类型、双方、当前负责人、当前阶段停留时间和申诉倒计时。超时和执行失败使用明确风险标识。

### 9.3 案件详情

采用“案件卷宗 + 固定裁决工作台”布局：

- 左侧连续展示订单摘要、双方资料、陈述、申诉、证据和时间线。
- 右侧固定展示负责人、申诉期限、当前可用动作以及领取、转交或裁决表单。
- 窄屏时工作台移动到正文下方，不横向压缩主要信息。
- 裁决表单即时校验金额和信用调整，并在提交前展示完整影响预览。
- 初裁和终裁均需要二次确认。
- 提交成功后锁定裁决记录并刷新案件时间线。

## 10. 错误处理

业务错误必须区分：

- 非订单相关方或无裁决权限。
- 案件状态已变化。
- 申诉期限已过。
- 当前阶段已经提交过材料或裁决。
- 二次申诉没有新增理由或证据。
- 退款、结算或信用调整方案非法。
- 案件正在由其他管理员处理。
- 内部执行任务失败。

前端对权限和校验错误保留当前输入；对状态冲突刷新最新案件；对执行失败展示任务状态、失败摘要和安全重试入口。

## 12. 后续演进

- 接入微信支付退款、商户结算和真实账本时，实现新的执行任务适配器。
- 引入 BullMQ 和 Transactional Outbox 后，将内部任务消费迁移到独立 Worker。
- 用户详情页增加投诉记录摘要和案件详情跳转。
- 根据运营规模增加 SLA、自动分配和客服绩效统计。

这些演进不改变当前纠纷聚合、状态机、共享 API 契约和后台信息架构。
