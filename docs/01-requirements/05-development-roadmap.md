# PetCare 当前状态与开发路线图

> 最后核对：2026-08-27
> 本文负责记录当前完成度、开发顺序和周期边界；产品范围仍以 [PRD](./01-prd.md) 为准，页面验收仍以 [原型规格](./04-prototype-specification.md) 为准。

## 1. 文档职责

- 本文是开发阶段与先后顺序的唯一维护入口。
- GitHub Issues 记录当前周期的具体执行状态；只拆当前周期和下一周期，不提前创建大量微任务。
- `docs/superpowers/plans/` 中的历史计划只保留为实施记录，未勾选项不代表当前待办。
- 每个周期结束时更新本文的实际结果、下一周期范围和估算偏差。

## 2. 估算口径

- 1 个标准周期为 10 个工作日。
- 默认产能为 1 名全栈开发者配合 AI，复用当前仓库已有实现。
- 当前只估算个人开发版范围。微信支付、实名认证、人脸识别、小程序审核等依赖外部主体、账户、合同或审批的能力不进入近期排期。
- 两名开发者可以并行处理同一纵向功能的 Server 与 Miniapp 工作，但依赖和联调决定了总时长不能简单减半。

## 3. 当前结论

截至 2026-08-27，内容社区 Cycle 1–3 已在本地线性 `master` 完成首发候选：课堂文章、受控社区发布与媒体、审核处置、点赞、评论、最小互动通知以及社区搜索/筛选均已接入真实数据，并由隔离纵向 E2E 串联验证。Cycle 4 已完成 Pet 共享契约、本人 CRUD、领域专用宠物图片后端以及 Miniapp 列表、详情和编辑的本地代码候选；旧 `age` 数据兼容迁移、所有权拒绝、受订单引用删除保护，以及图片类型、大小、数量、事务绑定、失败清理和跨账户迟到响应隔离边界已通过本地定向验证。H5 与微信小程序目标构建通过，隔离纵向 E2E 已使用真实 Server、Miniapp、一次性数据库 schema 和仅测试进程启用的本地对象存储替身，验证创建、两次上传、页面编辑与读取、越权拒绝、重复命令以及显式和随档案清理。

项目当前按**个人、非商业、可本地验收的产品原型**收窄。服务者实名认证/资格审核、公开悬赏交易、接单履约、微信支付、退款、结算、提现、B2C 派单和生产服务内测全部暂停，不再把 Cycle 5 作为下一执行节点。真实腾讯 COS、生产短信、微信生产登录和小程序发布属于可选外部集成，也不再作为个人版完成门禁。Miniapp 已移除静态悬赏、服务订单、钱包、优惠券和服务者入口；Website 已移除商业公开路由、默认内容与兜底文案。下一批处理 Admin/Server 默认商业入口隔离；数据库中既有的已发布官网内容仍须通过单独、可审计的内容发布流程处理。

“本地首发候选完成”不等于已经生产发布，也不代表可以对外经营宠物服务或处理真实资金：远端 CI 当前仍在作业步骤执行前失败，目标环境也尚未发布验收。个人版仅允许本地开发、演示和自动化验收；内容社区范围从此固定，不追加关注、转发、推荐或实时聊天。

## 4. 当前产品顺序与范围收敛

### 4.1 第一阶段：内容社区首发

先交付以下能力：

- 萌宠课堂文章列表、分类、搜索和详情，直接复用现有 Admin 发布及公开读取能力；
- 登录用户提交文字和图片动态，新内容先审核后公开；
- 社区列表、详情、作者删除、举报、管理员通过/驳回/下架；
- 点赞、评论和最小互动通知；
- 发布频率、媒体类型和大小限制，以及加载、空、错误和禁用状态。

开放 UGC 不是零治理功能。举报、审核、下架、限流和隐私安全属于社区首发范围，不能作为后续优化推迟。媒体上传复用现有存储边界并按内容领域实现，不建设通用上传平台。

以下能力不进入内容社区首发：

- 实时聊天、视频直播、复杂推荐算法和动态转发；
- 宠物档案、服务者认证和悬赏交易；
- 用户钱包、优惠券和自助提现；
- 高级运营分析和 10000 并发目标。

### 4.2 个人开发版当前范围

当前版本只交付不依赖企业主体、真实资金或生产审批的能力：

- 本地账户与会话、个人资料和本人宠物档案；
- 萌宠课堂、受控社区发布、审核、举报、互动和最小站内通知；
- Admin 内容与权限管理、Website 内容读取，以及本地 Docker Compose 运行；
- 隔离数据库、隔离媒体替身和明确测试账号下的自动化验收。

本地测试数据只用于验证代码，不能包装成真实服务者、真实订单、真实收益或真实运营数据。腾讯云 COS、生产短信、微信生产登录等外部集成只有在个人可以合法、稳定取得对应账户时才按可选增强处理，缺少它们不阻塞个人版。

### 4.3 暂停的商业服务范围

以下能力保留为未来商业版产品设想，但不进入当前实现、排期或完成度：

- 服务者实名认证、人脸识别、资质审核、评分资格和对外招募；
- 公开悬赏、接单、SOP 履约、服务监控、取消、评价和投诉裁决闭环；
- 微信支付、退款、对账、平台分账、结算、提现、钱包、优惠券和收费配置；
- B2C 平台定价、自动派单、服务保障、保险及规模化运营；
- 需要生产主体、外部合同、合规材料或公开审核的发布与经营活动。

仓库中已存在的相关模型、接口、静态页面或历史原型不等于当前能力。个人版界面不得提供可点击的交易入口，也不得使用“已认证”“可接单”“服务进行中”“可提现”等文案制造已上线印象。未来恢复商业版前，必须由用户重新确认主体条件、目标市场、合规责任和真实第三方账户，再重新估算和拆解。

## 7. 执行规则

1. 每个 Issue 必须交付一个可验收的纵向结果，不按“先写完全部后端、再做全部前端”拆层。
2. 每名开发者同时只进行 1 个主任务；被阻塞时先处理阻塞，不另开无关页面。
3. 新任务必须说明依赖、权限边界、失败状态和验收命令；没有这些信息则保持 `needs-triage`。
4. 页面存在不等于功能完成；只有真实数据、加载/空/错误/禁用状态和关键测试全部一致才算交付。
5. 不可用控件必须在视觉、光标、无障碍语义和行为上同时不可用，不能保留误导性点击反馈。
6. 每个周期只运行与改动风险匹配的检查；发布候选和核心交易闭环再运行完整 CI 与相关 E2E。
7. 默认只执行第 6 节队列；禁止从历史 PRD、原型或未完成页面自动恢复商业服务任务。

## 8. 主要风险
