# PetCare 当前状态与开发路线图

> 最后核对：2026-08-26
> 本文负责记录当前完成度、开发顺序和周期边界；产品范围仍以 [PRD](./01-prd.md) 为准，页面验收仍以 [原型规格](./04-prototype-specification.md) 为准。

## 1. 文档职责

- 本文是开发阶段与先后顺序的唯一维护入口。
- GitHub Issues 记录当前周期的具体执行状态；只拆当前周期和下一周期，不提前创建大量微任务。
- `docs/superpowers/plans/` 中的历史计划只保留为实施记录，未勾选项不代表当前待办。
- 每个周期结束时更新本文的实际结果、下一周期范围和估算偏差。

## 2. 估算口径

- 1 个标准周期为 10 个工作日。
- 默认产能为 1 名全栈开发者配合 AI，复用当前仓库已有实现。
- 周期估算只包含工程工作，不包含微信支付、实名认证、人脸识别、小程序审核等外部审批等待时间。
- 两名开发者可以并行处理同一纵向功能的 Server 与 Miniapp 工作，但依赖和联调决定了总时长不能简单减半。

## 3. 当前结论

项目并非“什么都没做”，而是建设顺序失衡：工程基础、官网和部分 Admin 能力已经较完整，Miniapp 主要业务仍停留在静态页面。当前产品策略调整为“先发布内容社区，再建设服务交易”：先复用已有课堂文章能力，补齐受控社区交流，形成可使用的低门槛产品；之后再进入需要服务者资质、SOP 和资金安全的悬赏闭环。

这个顺序能缩短首个可用版本的时间，但不会减少悬赏业务本身的工作量，也会推迟对 O2O 核心商业假设的验证。内容社区首发必须固定范围，不能演变成无限扩张的社交平台。

## 4. 当前产品顺序与范围收敛

### 4.1 第一阶段：内容社区首发

先交付以下能力：

- 萌宠课堂文章列表、分类、搜索和详情，直接复用现有 Admin 发布及公开读取能力；
- 登录用户提交文字和图片动态，新内容先审核后公开；
- 社区列表、详情、作者删除、举报、管理员通过/驳回/下架；
- 点赞、评论和最小互动通知；
- 发布频率、媒体类型和大小限制，以及加载、空、错误和禁用状态。

开放 UGC 不是零治理功能。举报、审核、下架、限流和隐私安全属于社区首发范围，不能作为后续优化推迟。媒体上传复用现有存储边界并按内容领域实现，不建设通用上传平台。

以下能力不进入内容社区首发：

- 实时聊天、视频直播、复杂推荐算法和动态转发；
- 宠物档案、服务者认证和悬赏交易；
- 用户钱包、优惠券和自助提现；
- 高级运营分析和 10000 并发目标。

### 4.2 第二阶段：C2C 悬赏服务 MVP

内容社区首发后，固定社区范围并转入 C2C 悬赏模式。服务过程先使用领域专用的照片/短视频凭证和轮询刷新，不建设实时监控基础设施。对外真实服务内测必须包含支付、退款和内部结算；仅内部演示时可以使用明确标识的测试账务，但不得宣称为生产资金闭环。

## 5. 开发周期

### 5.1 内容社区首发

| 周期              | 目标               | 主要任务                                                                                                    | 退出标准                                                                  |
| ----------------- | ------------------ | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Cycle 0（3-5 天） | 收口基线与任务治理 | 修复格式、lint、类型和工具链测试；定位远端 CI；绿色后推送全部本地领先提交；建立路线图 Issue 与 Cycle 1 任务 | 本地必要门禁和 GitHub CI 通过；远端 `master` 与本地同步；没有游离开发任务 |
| Cycle 1           | 萌宠课堂真实接入   | 接入现有文章列表/详情接口；补分类、搜索、加载与错误状态；连通 Admin 发布/下线                               | Admin 发布后 Miniapp 可读取，文章下线后不可访问，静态课堂数据全部移除     |
| Cycle 2           | 受控社区发布       | 用户动态提交、领域媒体上传、待审核状态、公开列表/详情、作者删除、举报、Admin 审核与下架、发布限流           | 未审核内容不公开；作者、举报人和管理员权限隔离；违规内容可追踪下架        |
| Cycle 3           | 社区互动与首发     | 点赞、评论、最小互动通知、内容搜索/筛选、内容社区纵向 E2E、运营与隐私检查                                   | 用户可完成发布→审核→互动；失败状态可恢复；内容社区可独立发布              |

按默认产能，内容社区首发需要 **3 个标准周期，即约 6 周**，加上 Cycle 0 共约 7 周。首发后必须根据真实内容供给和使用反馈决定是否继续扩展；没有明确证据时直接进入 Cycle 4，不追加推荐、转发或实时聊天。

### 5.2 C2C 悬赏服务 MVP

| 周期     | 目标                   | 主要任务                                                                           | 退出标准                                                     |
| -------- | ---------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Cycle 4  | 真实宠物档案           | Pet 共享契约、鉴权 CRUD、领域专用图片上传、Miniapp 列表/详情/编辑接入              | 用户可管理自己的宠物；越权访问被拒绝；订单能引用真实宠物     |

| Cycle 9  | 取消、评价与投诉入口   | 取消时限规则、评价与评分汇总、Miniapp 投诉/申诉入口；复用现有投诉裁决后台          | 正常完成、取消和争议三条路径都有明确终态和审计记录           |
| Cycle 10 | 支付与退款             | 微信支付单、回调验签、幂等、退款、异常补偿与对账基础                               | 重复回调不重复记账；取消/裁决能产生可追踪退款结果            |
| Cycle 11 | 结算与收入             | 服务者应结算金额、冻结/解冻、收入明细、后台人工处置                                | 完成订单可进入结算；争议订单保持冻结；服务者可查看真实收入   |
| Cycle 12 | 服务内测发布           | 核心纵向 E2E、安全/隐私复核、监控告警、备份恢复演练、种子数据与内测手册            | 两类用户可在目标环境完成完整悬赏服务；关键失败可观测、可恢复 |

调整顺序后，C2C 服务内测预计从当前起需要约 **11-13 个标准周期，即 22-26 周**。相比直接开发悬赏，服务闭环顺延约 6 周；支付、实名和审核等待仍可能增加日历时间。

## 7. 执行规则

1. 每个 Issue 必须交付一个可验收的纵向结果，不按“先写完全部后端、再做全部前端”拆层。
2. 每名开发者同时只进行 1 个主任务；被阻塞时先处理阻塞，不另开无关页面。
3. 新任务必须说明依赖、权限边界、失败状态和验收命令；没有这些信息则保持 `needs-triage`。
4. 页面存在不等于功能完成；只有真实数据、加载/空/错误/禁用状态和关键测试全部一致才算交付。
5. 不可用控件必须在视觉、光标、无障碍语义和行为上同时不可用，不能保留误导性点击反馈。
6. 每个周期只运行与改动风险匹配的检查；发布候选和核心交易闭环再运行完整 CI 与相关 E2E。
7. Cycle 3 后默认转入悬赏主链；只有真实使用数据和明确产品决策才能扩大社区范围。

## 8. 主要风险

- 微信支付、实名认证、人脸识别和小程序审核会引入外部账号、合同、资质与等待时间。
- 开放社区需要持续的内容审核、举报处理、限流和隐私保护；不能因为不涉及服务者资质就视为零治理成本。
- 内容活跃度不能证明用户愿意购买宠物服务；社区阶段固定为 3 个周期，避免推迟核心交易验证。
- 资金、退款、隐私、订单并发和数据迁移不能用“先跑起来”替代正确性与审计。
- 内容社区、服务交易和 B2C 平台不得并行扩张；每个阶段达到退出标准后再进入下一阶段。
- 当前远端 CI 无法提供有效证据；在修复前不能宣称任何新提交可发布。
