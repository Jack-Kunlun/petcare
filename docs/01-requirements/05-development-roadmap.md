# PetCare 当前状态与开发路线图

> 最后核对：2026-08-31
> 本文负责记录当前完成度、开发顺序和周期边界；产品范围仍以 [PRD](./01-prd.md) 为准，页面验收仍以 [原型规格](./04-prototype-specification.md) 为准。

## 1. 文档职责

- 本文是开发阶段与先后顺序的唯一维护入口。
- GitHub Issues 记录当前周期的具体执行状态；只拆当前周期和下一周期，不提前创建大量微任务。
- `docs/superpowers/plans/` 中的历史计划只保留为实施记录，未勾选项不代表当前待办。
- 每个周期结束时更新本文的实际结果、下一周期范围和估算偏差。

## 2. 估算口径

- 1 个标准周期为 10 个工作日。
- 默认产能为 1 名全栈开发者配合 AI，复用当前仓库已有实现。
- Cycle 5–7 仍按不处理真实资金、可在隔离环境验收的原口径执行。Cycle 8 以后涉及资格写入、支付、结算和生产入口的工期，必须在对应主体、账户、合同、合规责任与目标环境就绪后单独确认。
- 两名开发者可以并行处理同一纵向功能的 Server 与 Miniapp 工作，但依赖和联调决定了总时长不能简单减半。

## 3. 当前结论

截至 2026-08-30，内容社区 Cycle 1–3 已在线性 `master` 完成首发候选：课堂文章、受控社区发布与媒体、审核处置、点赞、评论、最小互动通知以及社区搜索/筛选均已接入真实数据，并由隔离纵向 E2E 串联验证。Cycle 4 已完成 Pet 共享契约、本人 CRUD、领域专用宠物图片后端以及 Miniapp 列表、详情和编辑；旧 `age` 数据兼容迁移、所有权拒绝、受订单引用删除保护，以及图片类型、大小、数量、事务绑定、失败清理和跨账户迟到响应隔离边界已通过定向与纵向验证。H5 与微信小程序目标构建通过，隔离纵向 E2E 已使用真实 Server、Miniapp、一次性数据库 schema 和仅测试进程启用的本地对象存储替身，验证创建、两次上传、页面编辑与读取、越权拒绝、重复命令以及显式和随档案清理。

个人、非商业、可本地验收的产品基线已经收口。2026-08-30 用户明确恢复悬赏、订单与 SOP 开发；Cycle 5–6 已于 2026-08-31 在默认关闭的隔离边界完成，交付真实资格硬门禁、重复意向幂等、唯一服务者确认和订单状态迁移。2026-08-31 用户进一步明确恢复资格写入、支付、结算与商业入口；这些能力按 Cycle 8–11 分阶段实现，未完成真实纵向链路和目标环境发布门禁前不得先行开放生产入口。禁止用假认证、假支付或测试账务代替真实依赖；Cycle 7 已由 [#54](https://github.com/Jack-Kunlun/petcare/issues/54) 启动。

此前对 Miniapp、Website、Admin、Server 与共享契约的商业残留清理仍然有效：历史页面和应用层代码只作审计参考，不整批回退；保留的 Prisma Schema 与 migration 继续作为数据兼容基础。真实腾讯 COS、生产短信、微信生产登录以及小程序审核/发布不作为隔离开发门禁，但它们是否满足生产发布条件必须单独确认。

长期本地 Compose 已使用显式 `local` 媒体 provider 和 `petcare-local-media-data` named volume，管理员/用户头像、宠物、社区与官网素材复用服务端管理的对象键和只读 `/media/` 出口。真实容器验收已确认宠物与社区图片可上传、读取、跨 Server/网关容器重建保留，并在删除后返回 404；腾讯云 COS 仅在显式选择 `tencent-cos` provider 时启用。

2026-08-29，提交 `a82aef082085f4aacc73491fa39311de03ea8745` 的远端 CI、生产部署工作流和微信小程序上传工作流均成功。该事实证明当前提交通过远端门禁、完成部署事务并上传到微信公众平台，但不等于目标环境已经独立功能验收，也不等于小程序已审核通过或公开发布。已部署能力仍限定为个人、非商业范围，不得对外经营宠物服务或处理真实资金；内容社区范围从此固定，不追加关注、转发、推荐或实时聊天。

2026-08-30，生产 Web 表面的独立只读冒烟通过：Website、Server、Admin、HTTP 到 HTTPS 跳转、未授权鉴权边界和腾讯 COS 公开素材读取均符合预期，过程中未写入生产测试数据。Miniapp 经用户明确决定不纳入本轮冒烟，仍只记录上传成功；微信审核、体验版和公开发布状态未核验，不得据此宣称已审核或已发布。

## 4. 当前产品顺序与范围收敛

### 4.1 第一阶段：内容社区首发

先交付以下能力：

- 萌宠课堂文章列表、分类、搜索和详情，直接复用现有 Admin 发布及公开读取能力；
- 登录用户提交文字和图片动态，新内容先审核后公开；
- 社区列表、详情、作者删除、举报、管理员通过/驳回/下架；
- 点赞、评论和最小互动通知；
- 发布频率、媒体类型和大小限制，以及加载、空、错误和禁用状态。

开放 UGC 不是零治理功能。举报、审核、下架、限流和隐私安全属于社区首发范围，不能作为后续优化推迟。媒体上传复用现有存储边界并按内容领域实现，不建设通用上传平台。

以下能力不进入内容社区首发：

- 实时聊天、视频直播、复杂推荐算法和动态转发；
- 宠物档案、服务者认证和悬赏交易；
- 用户钱包、优惠券和自助提现；
- 高级运营分析和 10000 并发目标。

### 4.2 已交付的个人版基线

当前版本只交付不依赖企业主体、真实资金或生产审批的能力：

- 本地账户与会话、个人资料和本人宠物档案；
- 萌宠课堂、受控社区发布、审核、举报、互动和最小站内通知；
- Admin 内容与权限管理、Website 内容读取，以及本地 Docker Compose 运行；
- 隔离数据库、隔离媒体替身和明确测试账号下的自动化验收。

本地测试数据只用于验证代码，不能包装成真实服务者、真实订单、真实收益或真实运营数据。腾讯云 COS、生产短信、微信生产登录等外部集成只有在个人可以合法、稳定取得对应账户时才按可选增强处理，缺少它们不阻塞个人版。

### 4.3 分阶段恢复的 C2C 与交易范围

Cycle 5–7 恢复以下工程能力：

- 宠物主人创建本人宠物的悬赏，并读取不含精确地址和私密备注的安全列表/详情；
- 具备真实资格记录的服务者提交意向，由主人确认后形成唯一履约关系和可审计订单状态；
- 已确认服务者按冻结步骤执行 SOP，主人只读查看履约证据。

Cycle 8–11 依次恢复资格申请与审核写入、支付退款、结算提现及最终商业入口。隔离开发阶段默认关闭商业 Server 路由和 Miniapp 入口；任何入口只在其真实纵向链路、外部账户与目标环境验收通过后开放。外部依赖未就绪时必须失败关闭，本地测试数据只能存在于一次性隔离环境，不能包装成正式认证、支付、订单或收益。B2C、评价投诉、人脸识别及未列入下表的商业能力仍不在当前范围。

### 5.3 C2C 服务工程恢复

| 周期     | 目标               | 主要任务                                                                                      | 退出标准                                                                          |
| -------- | ------------------ | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Cycle 5  | 悬赏最小纵向链路   | 默认关闭的 Server 能力、本人宠物悬赏创建、我的悬赏、安全列表/详情、Miniapp 真实数据与隔离 E2E | 只允许活跃且资料完整的主人为本人宠物发布；私密地址/备注不公开；关闭态无可访问入口 |

| Cycle 7  | SOP 履约纵向链路   | 下单冻结步骤、服务者逐步提交证据、主人只读查看、步骤权限和顺序                                | 只有订单服务者可执行；证据与步骤状态可追踪；隔离 E2E 串联悬赏、确认和 SOP         |

| Cycle 9  | 支付与退款闭环     | 支付单、微信预支付、签名回调、幂等状态迁移、退款与对账                                        | 金额以整数分冻结；伪造/重放回调失败；真实商户沙箱或目标环境纵向验收通过           |
| Cycle 10 | 结算与提现闭环     | 不可变账务、服务者结算、提现门禁、失败补偿、对账和审计                                        | 资金守恒；重复命令不重复入账；差错可追踪、可重试且不得静默丢失                    |
| Cycle 11 | 商业入口发布       | 汇总资格、履约、支付与结算发布门禁，恢复真实导航、运行开关、监控和应急停止                    | 所需主体/账户/合同/合规责任齐备；目标环境全链路与回滚演练通过后才允许生产开放     |

Cycle 8–11 是 2026-08-31 的新恢复决定，不反向扩大 Cycle 7。Cycle 6 可以用一次性测试数据验证资格门禁的通过路径，但正式数据不得由种子、占位接口或模拟回调制造。评价投诉、人脸识别和 B2C 仍未恢复。

节点 3 未修改数据库 Schema 或既有 migration。`local` provider 只用于开发/测试，普通 `docker compose down` 会保留媒体 named volume；真实 COS 的凭据、网络、Bucket 权限与 CDN 仍是可选外部集成验收，不属于个人版完成门禁。

节点 5 的证据和候选清单见[个人版历史数据库与遗留数据只读审计](../05-database-design/02-personal-scope-data-audit.md)。本地空表不能替代其他环境审计；只有确认全部数据源、完成备份恢复演练、审批非空记录处置并解除 `Order` 当前引用后，才能另建高风险 migration 任务。节点 6 与数据库 migration 必须独立提交和验收。

## 7. 执行规则

1. 每个 Issue 必须交付一个可验收的纵向结果，不按“先写完全部后端、再做全部前端”拆层。
2. 每名开发者同时只进行 1 个主任务；被阻塞时先处理阻塞，不另开无关页面。
3. 新任务必须说明依赖、权限边界、失败状态和验收命令；没有这些信息则保持 `needs-triage`。
4. 页面存在不等于功能完成；只有真实数据、加载/空/错误/禁用状态和关键测试全部一致才算交付。
5. 不可用控件必须在视觉、光标、无障碍语义和行为上同时不可用，不能保留误导性点击反馈。
6. 每个周期只运行与改动风险匹配的检查；发布候选和核心交易闭环再运行完整 CI 与相关 E2E。
7. 默认只执行第 6 节当前节点；后续 Cycle 8–11 只能按本文顺序单独启动，历史 PRD、原型或未完成页面仍不能自动扩大范围。

## 8. 主要风险

- 服务者资格来源、支付商户、结算主体、合同与运营责任尚未全部补全，因此 Cycle 7 及后续恢复只能在默认关闭的隔离边界开发，不能据此提前对外经营。
- 开放社区需要持续的内容审核、举报处理、限流和隐私保护；不能因为不涉及服务者资质就视为零治理成本。
- 历史静态页面和演示数据可能误导使用者认为认证、服务订单或钱包已上线；恢复时必须接真实数据，不能复活假页面。
- 测试账务、测试认证和模拟回调只能存在于隔离测试中，不得进入个人版正式数据或产品文案。
- 远端 CI、生产部署事务和小程序上传成功不能替代独立目标环境冒烟，也不能证明微信审核通过或公开发布。
